1. What the Problem Statement Asks

“Development of a Real-time Airfare Price Index for India through Automated Web Scraping of Airline and Online Travel Aggregator Portals for Augmentation of the Consumer Price Index (CPI).”

The core problem: India’s CPI (Consumer Price Index) is the number RBI uses to set interest rates and measure inflation. The “Transport & Communication” sub-group inside CPI includes air travel — but currently, airfare prices are collected manually from a few ticketing offices. Since 90%+ of domestic tickets are sold online and airline pricing is dynamic (the same DEL→BOM flight can vary 200–400% in a single day), manual collection structurally misses what Indian consumers actually pay.

⚠️ The Core GapManual collection captures a single price at a single point in time. It structurally misses the entire lead-time elasticity curve — the pattern of how prices change as the booking date approaches the travel date. This means RBI is setting monetary policy on structurally incomplete inflation data for air travel.

What They Want Us to Build

  1. An automated web-scraping engine that collects airfares from 5 airlines + 6 OTAs
  2. A data cleaning pipeline that removes outliers, handles missing values, and separates base fare from taxes
  3. An index-construction module (the “APIx”) using DGCA traffic weights
  4. An interactive dashboard showing price trends, heatmaps, lead-time elasticity
  5. A REST API for NSO/RBI to consume
  6. At least 30 days of back-tested results against DGCA monthly average fares

4.2 Scraping Engine

  • Each source has its own adapter module (e.g., scrapers/akasa.py)
  • All extend a common FareScraper base class
  • Uses Playwright (headless Chromium)
  • Rate-limited to 60 req/hr/host
  • Every request preceded by robots.txt check + politeness delay

4.3 Data Cleaning Pipeline

  1. Range Validation: Fares outside ₹500–₹50,000 rejected
  2. Modified Z-Score: Groups by route+window, MAD-based, flags |Z| > 3σ. Flagged — NOT deleted.
  3. IQR Detection: Second pass using Q1 − 1.5×IQR / Q3 + 1.5×IQR
  4. Deduplication: Removes exact duplicates on (source, origin, dest, date, carrier, flight, fare)
  5. Sold-out/Cancelled: Stored with availability_status=‘sold_out’ — never dropped

4.4 Reconstruction Engine

  • Anchored on DGCA TMU fares
  • Calibrated against live data
  • Carrier factors: IndiGo 0.95x, Air India 1.15x
  • Window multipliers: T+1 at 2.2x, T+45 at 0.75x
  • 5% Gaussian noise for realism
  • Every row hard-labelled RECONSTRUCTED

5. Index Construction — The Math

The APIx Formula

APIx = Sum(w_i x PR_i) x 100

wi = DGCA traffic weight | PRi = P(today) / P(base period) | 100 = base value

This is a modified Laspeyres index — same formula family used by NSO for CPI.

Booking Window Weights

WindowWeightReasoning
T+110%Last-minute business/emergency
T+720%Short-notice leisure/business
T+1526%Most common leisure window
T+3028%Advance leisure (largest share)
T+4516%Very early booking

Confidence Score

TrustScore = (actual_data_points / expected_data_points) x 100
Expected = 22 routes x 5 windows = 110 data points per run

6. What T+1, T+7, T+15, T+30, T+45 Mean

“T” = Today (the observation/scraping day).

  • T+1 = Flight departing tomorrow — most expensive (walk-up fare)
  • T+7 = Departing 7 days from now — short-notice
  • T+15 = Departing 15 days from now — base anchor (1.0x)
  • T+30 = Departing 30 days from now — typical advance
  • T+45 = Departing 45 days from now — early bird, cheapest

10. Forecasting Engine

  • Holt-Winters Exponential Smoothing (statsmodels)
  • Additive trend, 7-day forward predictions
  • Fallback: 7-day rolling mean if < 7 data points

Buy/Wait Signal

pct_change = (avg_predicted_3_days - current) / current x 100

> +0.5%  --> BUY NOW   (prices rising)
< -0.5%  --> WAIT      (prices dropping)
else     --> NEUTRAL   (prices stable)

11. Anomaly Detection

  1. Rolling mean + 2.5σ threshold per route+window
  2. Cross-reference sources: 2+ sources = GENUINE_SURGE, 1 source = DATA_ERROR
  3. Festival calendar check: Diwali, Christmas, Holi, Summer, Dussehra = SEASONAL_SPIKE

12. ATF Impact Analysis

19. Potential Judge Questions & Answers

Q1: “How do you handle websites that block scraping?”
We built a full compliance framework based on RFC 9309. Before any request, our ComplianceGate checks robots.txt, identifies the governing rule with exact line number, and records the decision. 7/11 sources are gated. We use Official GDS APIs (Amadeus/Duffel) and our Anchored Reconstruction Engine calibrated on DGCA/CPI. Every reconstructed fare is hard-labelled RECONSTRUCTED.
Q2: “Is your index accurate? How do you validate?”
We backtest against CPI Item 294 (actual airfare CPI from NSO) and DGCA TMU monthly averages. Metrics: Pearson correlation, MAPE, direction agreement, mean bias. Every index value has a confidence score.
Q3: “What is T+1, T+7, etc.?”
T = Today. T+1 = flight departing tomorrow, T+30 = 30 days out. Same DEL-BOM can cost ₹12,000 at T+1 vs ₹4,500 at T+30. This “lead-time elasticity” is the core gap in current CPI methodology.
Q4: “What if your scraper breaks?”
Failed observations are logged with fetch_failed status. Reconstruction fills the gap. Confidence score drops. Next run retries. Each adapter is isolated.
Q5: “How is this different from MakeMyTrip?”
MMT shows one fare for one search. We capture 22 routes x 5 windows x multiple sources x 3 runs/day. We decompose fares, detect anomalies, forecast trends, and compute a weighted index for CPI. We also reveal OTA convenience fee markups.
Q6: “Why LLaMA 3 instead of GPT-4?”
Open-source = no vendor lock-in. Can be hosted on-premises on government infra. Groq runs it at ~200 tok/sec. It is a decision-support tool with verification disclaimers.
Q7: “Walk me through one pipeline run.”
GitHub Actions triggers → scraping engine checks robots.txt for each source → scrapes allowed sources via Playwright → reconstruction for gated sources → cleaning (validation, outlier, dedup) → store in DB → compute APIx with DGCA weights → anomaly detection + forecasting → serve via REST API + dashboard.
Q8: “Can this scale to 100 routes?”
Yes. Route basket is a simple tuple in domain.py. Adding a route = one line. Pipeline, cleaning, index loop dynamically. DB uses route_key string, not fixed enum. 100 routes x 5 windows x 13 sources = ~6,500 obs/run — well within capacity.
Q9: “How do you prevent reconstructed data from biasing the index?”
Three safeguards: (1) Labelled RECONSTRUCTED, filterable by API consumers. (2) Confidence score separates live vs reconstructed counts. (3) Calibrated against live market conditions — prevents systematic bias.
Q10: “What’s your main USP?”
Ethical compliance (robots.txt for every source), lead-time elasticity (full T+1 to T+45 curve), and provenance transparency (every data point traceable to source + timestamp).
